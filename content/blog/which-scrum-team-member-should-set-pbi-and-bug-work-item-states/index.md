<p><font size="2" face="Segoe UI Light">This is a fairly common question, usually by teams new to Scrum. The <a href="http://www.scrum.org/scrum-guides" target="_blank" rel="noopener">Scrum Guide</a> clearly identifies the roles and their responsibilities. Team Foundation Server does not. It only identifies security groups and permissions.</font></p> <p><font size="2" face="Segoe UI Light">Teams that have been using Scrum for a while should answer: "Let the team decide". I’m good with that answer.</font></p> <p><font size="2" face="Segoe UI Light">For team members that don’t yet know where the rules of Scrum stop and self-organization begins, I provide the following guidance on </font><font size="2" face="Segoe UI Light">who should "flip the switch" at each state transition of a PBI or Bug work item type:</font></p> <ul> <li><font size="2" face="Segoe UI Light">Anybody on the Scrum Team (or perhaps beyond) should be able to create a PBI or Bug work item (state: <i>New</i>)</font></li> <li><font face="Segoe UI Light"><font size="2">The Product Owner should be the one to accept a PBI or Bug (state: <em>Accepted</em>)</font></font></li> <li><font face="Segoe UI Light"><font size="2">The Product Owner should be the one to remove a PBI or Bug (state: <em>Removed</em>)</font></font></li> <li><font size="2" face="Segoe UI Light">Anyone on the Scrum Team can set the state to <i>Committed</i> (so long as the Development Team forecasts that work for the Sprint)</font></li> <li><font size="2" face="Segoe UI Light">Anyone on the Scrum Team can set the state to <i>Done</i> (so long as the Product Owner accepts it)</font></li></ul> <p><font size="2" face="Segoe UI Light">Try this for a while. Get good at Scrum, TFS, and how they work together. As you retrospect and improve, your team will come up with a better approach.</font></p>
